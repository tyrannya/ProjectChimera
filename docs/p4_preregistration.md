## 0. Why this checkpoint, and what it is allowed to conclude

### 0.1 What the programme already ruled out

Four checkpoints answered no, and the answers narrow rather than close the space:

| checkpoint | information set | answer |
| --- | --- | --- |
| v4 | OHLCV14, MTST | economically negative |
| P2a | OHLCV14, four model families | the model family is not what is binding |
| P2b | `smc_v1` (causal market structure) | no incremental value |
| P2c | `chart_structure_v1` (causal chart structure) | no incremental value |
| P3 | `microstructure_v1` (trade-level flow) | no incremental value |

P2b and P2c were transformations of the same five numbers per hour. P3 changed
the *source* — individual executions rather than the candle — and still found
nothing that cleared the bar. That is the strongest negative in the programme,
and it is why the next checkpoint does not read the spot tape again.

It is also narrow. P3 established that **the current hourly `microstructure_v1`
representation of Binance spot `aggTrades` did not add robust value over OHLCV14
at 1h/6h over four adaptive folds of one asset**. It did not establish that
microstructure is useless, that L1/L2 order-flow imbalance is useless, that
shorter-horizon flow is useless, or that multi-timeframe information is useless.
None of those was tested and none of them is claimed here.

### 0.2 Why derivatives positioning and carry

Funding, open interest and basis are the first information this programme would
read that is **not a function of the spot tape at all**:

- **Funding** is a payment between leveraged longs and shorts. It is a price of
  positioning, set by the imbalance between them, and it exists whether or not
  a single spot trade prints.
- **Open interest** is the size of the outstanding leveraged book. It is a
  state, not a flow, and no amount of spot candle or spot trade data determines
  it: the same price path is compatible with a book that is building and one
  that is unwinding.
- **Basis** is a cost of carry — the perpetual's premium or discount to spot. It
  is the market's price for holding leverage over time.

Every family this programme has tested so far was a different reading of what
*happened to price*. This is a reading of *who is positioned and what it costs
them*, and that independence is what makes it a second experiment rather than a
finer version of the first.

**This preference was treated as a hypothesis and it survived.** The alternative
on the list was order-book / L1-L2 OFI. It is rejected for this checkpoint, and
the reason is about what the evidence would mean rather than about which is more
interesting: P3 has already tested the fine-grained-flow hypothesis at hourly
resolution and found nothing, so an OFI checkpoint over the same four blocks is
the likeliest of all the candidates to answer the same way, at several times the
acquisition cost — full-depth book reconstruction, not a daily archive. OFI is
not abandoned; it belongs after a positioning checkpoint and needs its own
contract.

### 0.3 What P4 is allowed to conclude — the hard constraint

**The four outer blocks are burned.** They have been read by v4 (five seeds),
P2a, P2b, the P2b ablation, the P2b regime description, P2c and P3. Nothing run
on them can confirm anything, and splitting them into more folds would
manufacture independence rather than find it. They are used here as an
*exploratory screen* and are labelled as such in every output.

**One pre-Styx region has never been scored**, and it is small:

| | |
| --- | --- |
| canonical rows | `[45802, 48211)` |
| candles | 2,409 |
| span | `2025-05-19T08:00` .. `2025-08-27T16:00` UTC (approximately 100 days) |
| size relative to one outer block | about half |
| scored by any committed artifact | **no** |
| readable from the committed research snapshot | **no** — it is truncated at row 45802 |
| ever sealed | **no** |

Rows `[48211, 48217)` exist and are pre-Styx but are **not** usable: their
6-candle labels close at or after the sealed instant, so reading them would
read a sealed price. `48211 + 6 = 48217 = research_rows` exactly.

That region is designated **P4-HOLD** and is used **once**, under the rules in
§9. Three things must be said about it plainly, because the temptation is to
say two of them and stop:

1. It is genuinely unobserved *in this repository*. No committed artifact scores
   it, and the committed snapshot physically does not contain it.
2. It was never *sealed*. It has always been inside the research region, so this
   repository cannot prove that no human ever looked at a chart of it. Styx is
   what a proof of that looks like, and this is not Styx.
3. It is one contiguous region, `n = 1`, of about 2,400 rows. At the trade
   coverage every prior checkpoint has shown, that is tens of trades, not
   thousands.

**Therefore: P4 cannot produce confirmatory evidence.** The best label available
to it is *single-region supported*, and §9 says what that does and does not
license. Saying so now, before any number exists, is the point of writing this
down now.

## 1. Research question

> **Does causal derivatives positioning and carry information — the Binance
> USD-M `BTCUSDT` perpetual's realised funding rate, its open interest, and its
> basis to spot — add usable incremental information beyond the frozen OHLCV14
> control, for the existing BTC/USDT 1h, 6-candle, cost-aware directional
> target?**

"Usable" means the same thing it has meant in every checkpoint since P2a: outer
net return after the existing round-trip costs, measured on the same rows as the
control, with the decision threshold selected on the inner block only.

"Causal" means every column is a function of observations that had already been
published at the instant the decision is made. §4 establishes that per feature.

### 3.0a The open-interest archive, corrected

The first version of this preregistration named a **monthly** metrics path.
Binance does not publish one. A preregistration that commits to a URL which
does not exist commits to nothing, and the correction belongs here — before any
probe and before any P4 number — because after either of those it would be a
source chosen against data.

| | |
| --- | --- |
| archive | `data.binance.vision/data/futures/um/daily/metrics/BTCUSDT/BTCUSDT-metrics-{YYYY}-{MM}-{DD}.zip` |
| granularity | **daily** — one archive per UTC day, each holding 5-minute rows |
| earliest intended availability | **2020-09-01** |
| columns read | `sum_open_interest` (contracts), `sum_open_interest_value` (notional) |

**2020-09-01 is an intent, not a measurement.** Nothing here has touched the
network. The probe establishes the real first available day from metadata only,
and a first day later than this one *narrows the sample universe* rather than
being worked around.

**A missing day is a missing day.** An archive that 404s, fails its checksum or
arrives short is never interpolated. One missing day removes 288 five-minute
snapshots, so under the 1-hour open-interest staleness bound (§3.4) **every hour
of that UTC day leaves the sample universe for every arm, the control
included**. Missing days are counted, reported per block, and fed to the
availability rule in §8.0.

**Coverage failure is fail-closed.** An archive that cannot be fetched or
verified stops the acquisition rather than being skipped, and a block that fails
the availability rule makes the checkpoint `not_evaluable` — see §9.0, which is
the row that says why that is not a negative result.

**The REST endpoint is diagnostic and fallback only.**
`fapi.binance.com/futures/data/openInterestHist` retains 30 days, so it cannot
build this history at all. It may spot-check a handful of recent archive rows.
It may **never** silently stand in for a missing archive day: a row sourced from
REST is not a row of the preregistered historical source, and an acquisition
that substituted one would be reporting a universe it did not have.

### 3.0b The funding archive's columns, fixed before the file is opened

Binance has published funding data under more than one column layout. A reader
that inferred the mapping at acquisition time would be deciding, *after seeing
the file*, which column is the rate — a researcher degree of freedom wearing the
clothes of an implementation detail. So the mapping is an allow-list, fixed
here, and `nn/p4_preregistration.py::FUNDING_CSV_COLUMN_POLICY` is the copy the
acquisition must read rather than restate.

| accepted layout (by exact column-name set) | settlement instant | realised rate |
| --- | --- | --- |
| `fundingTime`, `fundingRate` | `fundingTime` | `fundingRate` |
| `calc_time`, `funding_interval_hours`, `last_funding_rate` | `calc_time` | `last_funding_rate` |
| `calc_time`, `last_funding_rate` | `calc_time` | `last_funding_rate` |

A recognised layout may carry extra columns; they are ignored. A **headerless**
file is accepted only in the single unambiguous two-column shape, and only when
its first column parses as an epoch instant inside the archive's own calendar
period — the same "let the archive's period decide the unit" test
`nn.trade_aggregates.resolve_epoch_unit` applies to trades.

**Anything else is a refusal.** Do not infer a mapping, do not fall back to
positional order, and do not read the REST endpoint instead. Extending the
allow-list is a commit that moves the preregistration hash, and is permitted
only while no P4 outer number exists.

### 3.1 Timestamp semantics

| field | column | what the instant means |
| --- | --- | --- |
| funding | `fundingTime` | the **settlement instant**: 00:00, 08:00, 16:00 UTC. The rate is final at that instant. |
| open interest | `create_time` | the instant of a **5-minute snapshot** of the outstanding book. A state, not an interval. |
| perpetual price | `open_time` | the candle's **open**. Its close is complete at `open + 1h`. |
| spot price | `date` | the candle's **open**. Its close is complete at `open + 1h`. |

Everything downstream is int64 UTC nanoseconds, as in P3.

### 3.2 Publication and availability

- The realised funding rate is final at its settlement instant. The
  continuously published **predicted** funding rate is *never read* — it is a
  forecast, it is revised, and using it would put a revised number into a
  historical row.
- Open-interest snapshots are published at their own instants and are not
  revised.
- Perpetual klines are complete at the candle close and are not revised.

**Revisions.** None of these three sources is expected to revise a historical
value. The acquisition records, per archive, the published checksum and the byte
digest actually fetched — the same machinery `tools.export_trade_snapshot` uses
— so a source that *does* revise produces a digest mismatch against a re-fetch
rather than a silent change. A snapshot is exported once, verified, and frozen.

### 3.3 Resampling to the hourly grid

- **Funding** is not resampled. Row `t` reads the most recent settlement visible
  to it (§4). This is holding a step function, not interpolation.
- **Open interest** is reduced to one observation per hour: the **last snapshot
  at or before `t`**. Not a mean over the hour — a mean is not a state anything
  was in, and it mixes information from inside the hour with the hour's own
  boundary.
- **Perpetual price** is already hourly and joins on exact timestamps.

### 3.4 Gaps, duplicates and staleness

Fail-closed, and identically for every arm:

- A **duplicate** timestamp is a rejection of the acquisition, not a
  de-duplication. Two rows claiming one instant means the reader cannot tell
  which is the observation. **As originally written this applied to every source
  without exception; §3.4a narrows it for one case in one source, and states why
  and when.**
- A **gap** does not get filled. It becomes staleness, and staleness has a
  bound:

| field | may be carried forward for at most | why |
| --- | --- | --- |
| funding | 9 hours | it is 8-hourly by construction; the extra hour is tolerance for a late archive row |
| open interest | 1 hour | a 5-minute snapshot missing for an hour is twelve missed snapshots |
| perpetual price | 1 hour | one candle |

- A row whose feature would need a stale-beyond-bound observation is **outside
  the sample universe for every arm, control included** (§6).
- No forward-fill crosses a boundary the OHLCV14 spine already treats as a
  segment break.
- Staleness is measured from the last **valid** observation. **As originally
  written every parsed row was an observation; §3.4d says which open-interest
  rows are, and states why and when.** The bound itself is untouched.

### 3.4a Source-protocol amendment A1 — exact duplicate metrics rows

**Status: amendment, not an original commitment.** Adopted after a bounded
inspection of real source archives, and before any P4 model fit, Stage-1 result,
outcome or holdout access existed. Everything else in this document was fixed
with no source file open. This was not, and that difference is recorded rather
than smoothed away.

**What the original rule said.** §3.4, as first written: *a duplicate timestamp
in any source is a rejection of the acquisition, not a de-duplication.* That rule
was written for the failure it names — two rows that *disagree*, where any choice
between them is a decision about the data made by the code reading it.

**What was then measured.** The official Binance USD-M `BTCUSDT` daily metrics
archives dated **2020-09-01** and **2020-09-02**:

| archive | data rows | distinct `create_time` | distinct complete rows |
| --- | --- | --- | --- |
| `BTCUSDT-metrics-2020-09-01.zip` | 576 | 288 | 288 |
| `BTCUSDT-metrics-2020-09-02.zip` | 576 | — | 288 |

Every 5-minute observation is published **twice**, and the paired rows are
identical across every column of the CSV. The defect is **exact row
duplication**, not conflicting observations — which is not the case the original
rule was written for. A reader that cannot tell which of two rows is the
observation must stop. A reader looking at two copies of one row has nothing to
tell apart, and nothing to choose between.

**Two archives were inspected. That is all that is claimed.** Nothing here
asserts that other metrics days are duplicated, that the duplication has a known
cause, or that it will persist. The rule is written for whatever the source
actually serves, day by day, and each day's outcome is counted.

**What the amendment permits, and only this.** The machine-readable rule is
`OPEN_INTEREST_DUPLICATE_POLICY` in
[`nn/p4_preregistration.py`](../nn/p4_preregistration.py), inside the hashed
payload:

- **Scope**: the `open_interest` field, from the Binance USD-M daily metrics
  archive, and no other source.
- **Grouping key**: `create_time`.
- **Acceptance**: rows sharing an instant are accepted only when the **complete
  published CSV row is identical across every column** — compared after schema
  validation, and including columns no `derivatives_v1` feature consumes. Two
  rows agreeing on `create_time`, `sum_open_interest` and
  `sum_open_interest_value` but differing anywhere else are **not** exact
  duplicates.
- **Normalisation**: N identical rows at one instant collapse to exactly one
  logical observation; the N − 1 removed rows are counted.
- **Conflicts**: if any field differs, **reject the acquisition**. Never the
  first row, never the last, never an average, never an inference.
- **Provenance**: `rows_read`, `observations_retained`,
  `exact_duplicate_rows_collapsed` and `duplicate_instants` are recorded per
  archive and summed in the snapshot manifest under
  `acquisition.open_interest_source_integrity`. A collapsed row never disappears
  silently, and the archive's own `sha256` and raw row count stay recorded beside
  the logical counts, so normalisation does not pretend the upstream bytes were
  different.
- **Other sources unchanged**: a duplicate timestamp in the **funding** or
  **perpetual klines** archive remains a rejection of the acquisition, with no
  normalisation of any kind. §3.4 stands unamended for both.
- **Schema first**: schema identity is validated before normalisation, so an
  archive whose header is not the preregistered one is refused for its schema and
  never reaches this rule.

**This intentionally moves the preregistration hash.** The amendment changes
source-ingest semantics, so it belongs in the hashed payload and not in prose
alone. The superseded hash — the one the original preregistration carried, before
`open_interest_duplicate_policy` entered the payload — is
`sha256:68ba94f49099c90772cc29d9ed6ea0cb1c4fb3b49a457924e9c3ca9f9af865a4`, and it
is recorded here and at the top of this document as history. No P4 cell, fit or
outcome was produced under it, and nothing may be produced under it now.

**This document is where the superseded hash lives.**
`data/research/p4_stage1_authorisation.json` carries only the *active* hash: it is
an interlock, and an interlock that names two designs invites the question of
which one it authorises. The answer is neither — its state is `not_authorised` —
but the file should not have to be read carefully to establish that.

**No outcome information motivated this.** No P4 model has been fitted, no
Stage-1 result exists, P4-HOLD is unspent and unread, and the sealed region is
untouched. The only information that entered this decision is the column layout
and row structure of two published archives — the same class of information
`--probe` was always designed to establish (§3.5, §3.6).

**What it does not change.** No feature, no window, no clip, no staleness bound,
no availability rule, no sample-universe condition, no Stage-1 geometry, no
holdout rule, no target, no cost model, no model configuration. An archive with
no duplicate rows produces byte-identically the same hourly table it produced
before.

metrics archives, A2 followed the acquisition attempt that inspection was a

the next source, and A4 followed the attempt that got past A3's boundary and
completed the download.

**A4 is not A1.** §3.4a decides which *published rows* are one logical row. A4
decides which of those logical rows are open-interest *observations*. They are
different questions about the same archive, they run in that order, and neither
subsumes the other.

**What the original rule said.** The original design had no notion of an invalid
observation at all. Every row that survived schema validation was an observation,
the only remaining question was how stale it was (§3.4), and a published zero
would have entered the hourly table as a real zero open-interest state. That
worked because nothing had ever read the source at row level, and the assumption
underneath it — that a published metrics row carries a positive open-interest
state — had never been checked.

**What forced the check.** The first full acquisition after A3 completed all
**1722** planned open-interest days and then failed during construction and
validation of the hourly table, with:

```

```

That check is original and unchanged. It fired because the acquisition had marked
an hour available on the strength of a published zero — which is exactly what it
exists to refuse. The failure is therefore a correct refusal by the protocol, and
what needed fixing was the protocol's silence about what such a row *is*.

**What the amendment fixes, and only this.** The machine-readable rule is
`OPEN_INTEREST_OBSERVATION_VALIDITY_POLICY` in
[`nn/p4_preregistration.py`](../nn/p4_preregistration.py), inside the hashed

- **Scope**: the `open_interest` field, from the Binance USD-M `BTCUSDT` daily

  untouched.
- **Order**: the rule applies **after** schema validation and **after** §3.4a's

  collapses identical repeats of one `create_time`, the two consumed numeric
  fields are parsed, and only then is each retained logical row classified. A zero
  row published twice identically is therefore collapsed by A1 **first** and
  classified once by A4 afterwards — which is what keeps A1's duplicate accounting
  a description of what the archive published.

  **if and only if** `sum_open_interest > 0` **and**
  `sum_open_interest_value > 0`. Both consumed metrics must be strictly positive.

  remains a real published source row for provenance and accounting. It **does
  not** enter the causal observation sequence, **does not** update the hourly
  last-observation reducer, is **not** replaced with another numeric value, is
  **not** interpolated, is **not** averaged, is **not** repaired from REST, is
  **not** repaired from a future observation, and **does not** on its own turn its
  archive or its UTC day into a §3.0a missing day.
- **Negative, non-finite or unparseable is a HARD FAILURE**, not an ordinary
  zero-invalid observation. None was observed, so none has a preregistered
  meaning, and a run that meets one has met something the inspection did not
  measure. It stops the acquisition.

  never applied backwards to hours the invalid run left unavailable.
- **Provenance**: `logical_observations`, `valid_positive_observations`,

### 3.5 Fail-closed acquisition and integrity

The acquisition follows P3's pattern exactly, and none of it is written yet:

1. `--plan` lists every archive it would fetch, **without touching the
   network**, and the plan is checked to contain no period that could hold an
   observation at or after the Styx instant. The seal is a property of the plan,
   not of a filter applied afterwards.
2. `--probe` measures a small number of real archives and projects the whole
   acquisition from measurements. **This is where the open-interest availability
   window gets established** — see §3.6.
3. Every archive is checksummed against its published digest where one exists,
   and its byte digest is recorded in the manifest either way.
4. The exported snapshot carries a manifest recording the contract, the seal,
   the file digest, the semantic hash, the per-source coverage, and the binding
   to the OHLCV snapshot — and a verifier recomputes every one of those claims
   rather than reading them.
5. The verifier runs **inside the only function that loads the source**, as
   `nn.p2b.load_trade_snapshot` does, so a corrupt source produces zero model
   fits by any path.
6. A **value-level cross-source check**: the perpetual's own hourly high, low
   and close are compared against the perpetual klines the basis is computed
   from, and the spot side against the committed candle history, on justified
   explicit tolerances. `tools.verify_trade_snapshot.cross_source_consistency`
   is the precedent.

### 3.6 The availability risk, named before it can be an excuse

`fapi`'s open-interest endpoint retains **30 days**. The daily `metrics` archive
(§3.0a) is the only route to a multi-year history, and **this repository has not
established when that archive begins.** Nothing here has touched the network;
2020-09-01 is the earliest day this preregistration intends to request, not a
day anyone has confirmed exists.

That is not a reason to postpone the preregistration; it is a reason to
preregister the consequence:

- The probe step establishes the actual availability window from metadata only.
- P4's **sample universe is the intersection** of OHLCV14 availability and
  derivatives availability (§6), and **the control is re-run on exactly that
  intersection**. The new information set does not get an unfair universe, and
  neither does the control.
- If the intersection cannot support the design — specifically, if it does not
  contain at least **two** of the four exploratory outer blocks *available under
  §8.0* **and** P4-HOLD available under the same rule — then **P4 is not run as
  designed**. The outcome is `not_evaluable` / `insufficient_coverage` (§9.0),
  the per-block coverage is recorded with it, and the checkpoint does not
  quietly become a two-fold checkpoint on a shorter history with the same
  decision rule.
- If the intersection excludes some exploratory blocks but satisfies the gate
  above, the *excluded* blocks are reported as excluded with their row ranges,
  and stage 1's fold count is over the blocks that survive — with the
  three-valid-fold requirement of §8 unchanged, which means a two-block
  intersection fails stage 1 by construction and the holdout is not opened.

## 4. Causality

For every feature, what was actually available at the decision instant.

**The decision instant.** In this repository a feature for row `t` is computed
from candle `t` and earlier; the label is `close[t+6] / close[t] - 1`; a trade at
row `t` is entered at the **close of candle `t`**, which is the instant
`t + 1h`. So a feature for row `t` may read anything published at or before
`t + 1h`.

### 4.1 Funding

Funding settles at 00:00, 08:00 and 16:00 UTC, and the realised rate is final at
the settlement instant.

> **Rule: a settlement at instant `T` is visible to row `t` if and only if
> `T <= t`** — the candle's *open*, not its close.

This is deliberately one hour more conservative than causality requires. The
08:00 settlement is final at 08:00 and the row whose open is 08:00 decides at
09:00, so the rule leaves a full hour between publication and use. It also makes
the rule independent of any assumption about how quickly the archive or the API
reflects a settlement, which is the assumption a leakage bug would hide in.

The **predicted** funding rate is not read at all, at any horizon.

### 4.2 Open interest

An open-interest snapshot is a state at its own instant, published as it is
taken and not revised.

> **Rule: row `t` reads the last snapshot with `create_time <= t`, and only if
> that snapshot is at most 1 hour older than `t`.**

Again `t` and not `t + 1h`. The 5-minute cadence means the binding snapshot is
typically 0–5 minutes before `t`, so the conservative rule costs almost nothing
and removes the boundary case entirely.

`drv_oi_log_change_24h` and `drv_oi_price_divergence` compare that snapshot with
the one 24 hours earlier, under the same rule. `drv_oi_price_divergence` also
reads `close_t` and `close_{t-24h}` — both candle closes at or before `t`, both
already in the control's own information set.

### 4.3 Basis

`drv_basis` is the perpetual's close at `t` over the spot close at `t`. Both are
candle closes at the same instant, both complete at `t + 1h`, and the row that
uses them decides at `t + 1h`. That is exactly the boundary every OHLCV14
feature already sits on, so basis is causal on the same terms the control is.

Two things this deliberately does *not* do: it does not use a mark price (which
is a smoothed index and a different object), and it does not use a quarterly
future (which would need contract-roll handling and a term-structure choice —
that is a menu, and §7 is about not having one).

### 4.4 What the leakage battery must show before any cell is scored

The P3 battery (`tests/test_p3_leakage.py`) is the template, and P4 must have
its equivalent **before its first fit**, not after its first result:

- append invariance — adding later observations must not change an earlier row;
- future-mutation invariance — changing a future observation must not change an
  earlier row;
- the funding-visibility boundary, exercised at exactly `T = t` and `T = t + 1s`
  with a positive control on each side;
- the open-interest staleness boundary, exercised at exactly 1 hour;
- gap resets across a spine segment boundary;
- a matrix rolled one hour forward must be **rejected**, not merely different;
- a Styx breach stopping the run before any fit;
- semantic-identity falsification: an edited source must change the digest.

## 5. Feature spec

Eight columns. Every window, constant and clip below is fixed here and **may not
be searched against a P4 outer result**, in this checkpoint or a later one.

| column | family | definition | window | clip |
| --- | --- | --- | --- | --- |
| `drv_funding_last` | funding | the most recent realised 8h funding rate visible at row t | — | [-0.01, 0.01] |
| `drv_funding_sum_9` | funding | sum of the last 9 realised settlements visible at row t (three days) | 9 | [-0.09, 0.09] |
| `drv_funding_z` | funding | (drv_funding_last − mean of the last 30 visible settlements) / (std of the same 30 + 1e-12) | 30 | [-5, 5] |
| `drv_oi_log_change_24h` | open interest | log(OI_t / OI_{t−24h}) on contract-count open interest | 24 | [-1, 1] |
| `drv_oi_notional_ratio` | open interest | OI notional at t over the mean OI notional of the last 168h | 168 | [0, 10] |
| `drv_oi_price_divergence` | open interest | log(OI_t / OI_{t−24h}) − log(close_t / close_{t−24h}) | 24 | [-1, 1] |
| `drv_basis` | basis | perpetual close at t over spot close at t, minus one | — | [-0.02, 0.02] |
| `drv_basis_z` | basis | (drv_basis − mean of the last 168h) / (std of the same 168h + 1e-12) | 168 | [-5, 5] |

**Why these and not more.** Three fields, two or three readings each: a level, a
recent accumulation or change, and a standardisation against the recent past.
That is the smallest set that can distinguish "funding is high" from "funding is
unusually high" and "the book is large" from "the book is growing". A larger
menu is not a richer hypothesis; it is more ways to report a subset afterwards.

**Why these are scale-free.** Every column is a rate, a log ratio, a ratio to a
trailing mean, or a z-score. None carries the dollar level of BTC, for the same
reason OHLCV14 does not: a model fitted on 2020 levels has no basis for 2025
levels. `drv_oi_notional_ratio` is the one that could have drifted — it is a
ratio to its own trailing mean precisely so that it does not.

**Known limitation, recorded now rather than discovered later.**
`drv_funding_z` and `drv_basis_z` standardise against a trailing window, which
means a regime with persistently elevated funding reads as "normal" after 30
settlements. That is a property of the representation and it is not fixed by
tuning the window. It goes on the `derivatives_v2` list, and it is not a
threshold to search.

## 6. Control and sample universe

### 6.1 The control

`ohlcv14`, the same 14 columns, from the same committed research snapshot, under
the same research contract `btc-usdt-1h-gen1` and the same contract hash.
Provenance is comparable in the strongest sense this repository has: the
snapshot's semantic prefix hash is identical, the fold geometry is identical, and
the control is **re-run inside P4's own process family** rather than copied from
P3 — which is how P2b, P2c and P3 each reproduced P2a's frozen seed-42 XGBoost
evidence, fold return for fold return.

### 6.2 The universe, and the fairness rule

A row is in P4's sample universe if and only if **all** of:

1. it is in the OHLCV14 research spine (past indicator warm-up, no NaN feature,
   its 6-candle label knowable without touching a sealed close);
2. every one of the eight `derivatives_v1` columns is defined at it, after the
   240-hour derivatives warm-up (the binding window is 30 funding settlements;
   the 168-hour windows are shorter);
3. no observation it depends on is stale beyond its §3.4 bound;
4. it does not bridge a spine segment boundary within any feature's window.

> **The universe is computed once and applied to every arm identically. The
> control is re-run on it.**

This is the audit's requirement and it is the one that is easiest to get wrong
by accident: if the derivatives arm is scored on the rows where derivatives data
happens to exist and the control on all rows, the comparison measures the
difference between two market periods and reports it as a difference between two
information sets.

Every P4 cell records the universe's row count, its first and last row, its
per-fold sample-index hashes, and the count of rows excluded by each of the four
conditions. `nn.p2b_compare`'s existing parity check refuses to join cells whose
per-fold sample-index hashes disagree, which makes the rule enforced rather than
promised.

### 6.3 Two snapshots, and why

Stage 1 and stage 2 read **different files**, and that is a structural guarantee
rather than a convention:

| stage | snapshot | rows | can it reach P4-HOLD? |
| --- | --- | --- | --- |
| 1 (exploratory) | the existing `btc_usdt_1h_gen1_snapshot_manifest.json` | `[0, 45802)` | **no** — the rows are not in the file |
| 2 (holdout) | a new `..._p4hold_snapshot_manifest.json`, exported once | `[0, 48211)` | yes, by design, once |

The stage-2 export is mechanical: same contract, same exporter, same verifier,
`48211 + 6 = 48217 = research_rows` so no label reaches a sealed close. It is
exported **after stage 1 is complete and frozen**, and the operator does not
inspect it — the run does. A `--plan`-style summary that reports row counts and
spans but no prices is the only thing anyone reads before the evaluation.

## 7. Target, horizon and costs

### 7.1 The target does not change

1h candles, 6-candle horizon, cost-aware three-class labels, `cost_threshold =
2 × (0.0005 + 0.0005) = 0.002`. Unchanged from v4, P2a, P2b, P2c and P3.

**Why, stated before results:**

- The question is *incremental information over the existing control*. The
  control's entire evidence base — P2a's frozen seed-42 numbers, and the
  reproductions of them in P2b, P2c and P3 — exists at 1h/6h and nowhere else.
  Moving the horizon replaces the control with an unmeasured object and changes
  two things at once.
- After four negative checkpoints, changing the horizon without a scientific
  reason is horizon shopping. The audit named it; this is the paragraph that
  forecloses it.

**The argument against, stated too, because it is real.** Funding settles every
8 hours and a 6-candle horizon spans at most one settlement, sometimes none. A
positioning signal whose mechanism is "funding pressure resolves over days" is
being asked about a 6-hour window. That is a genuine reason to prefer a longer
horizon — and it is a reason for a *future* checkpoint with its own control and
its own preregistration, not for changing this one after the fact. It is
recorded here as the first thing a P5 would change, and as a predeclared
limitation on how far a negative P4 generalises: **a negative P4 is evidence
about derivatives positioning at a 6-candle horizon, not about derivatives
positioning.**

### 7.2 Costs

Identical to every prior checkpoint, in both the label and the net return:
0.0005 taker fee and 0.0005 slippage per side, charged as a flat round-trip
subtraction of 0.002 from each trade's return.

**The traded instrument is unchanged.** P4 *reads* perpetual futures data; it
does not trade perpetuals. No funding is paid, because no perpetual position is
taken. A checkpoint that proposed trading the perp would need a different cost
model — funding, maintenance margin, a different fee schedule — and would be a
different question.

**Preregistered sensitivity.** Every arm reports net return at **1.0×, 1.5× and
2.0×** the round-trip cost (0.002, 0.003, 0.004). All three are reported for
every arm whatever they show. The headline is always 1.0×; the 1.5× figure
appears in one place in the decision rule (§9, the *supported* outcome) and it
is a **requirement**, never a rescue — there is no outcome in which a worse
result at 1.0× is redeemed by a better one at another multiplier.

## 8. Validation design and the decision rule

### 8.0 What "available in full" means, given a punctured daily feed

§3.6's gate said "two blocks in full" and "in full" had no operational meaning.
That is not a small gap. One missing daily open-interest archive removes a whole
UTC day of rows from every arm, so under a literal reading a single 404 anywhere
in five years makes every block unavailable and the checkpoint unrunnable —
and under a loose reading, any amount of loss can be waved through once the
numbers are in. Both readings are available to whoever is holding the result.

So the rule is arithmetic, and it is fixed before any probe:

> A block — an exploratory outer block, **or P4-HOLD, under the same rule** — is
> **available** when, after the §6.2 universe conditions are applied:
>
> 1. at least **98%** of its rows survive, **and**
> 2. no contiguous run of excluded rows exceeds **48 hours**.

Both numbers come from the mechanism rather than from a desired answer. An outer
block is 4,821 rows, so 2% is about 96 hours — four missing days scattered
across roughly seven months, which is a feed with holes and still the same
block. 48 hours is two consecutive missing archives; a longer unbroken outage
removes a *market episode* rather than a sample of hours, and a block missing an
episode is not that block.

A block that fails is **unavailable**, is excluded from stage 1's fold count
entirely, and is never included at a discount. Per-block coverage is computed
before any model is fitted and reported whatever the gate decides.

### 8.1 Why the old rule is not enough

P2b, P2c and P3 continued on "3 of 4 folds improved". Under an independent
p = 0.5 null,

> **P(X ≥ 3 of 4) = 5/16 = 0.3125.**

A coin clears that bar almost a third of the time. And the four folds are not
independent: fold `k`'s inner-validation block *is* fold `k−1`'s outer block, and
folds 2 and 3 train on earlier folds' outer rows, so a regime spanning a
boundary moves one fold's result and the next fold's selected threshold
together. The effective number of temporal observations is fewer than four.

The honest conclusion is not "use a better threshold". **At n = 4 dependent
folds no threshold has both a usable false-positive rate and usable power**: 4/4
gives α = 1/16 under the coin null and almost no power; 3/4 gives α = 5/16. So
P4 does not pretend to test anything on those blocks. It **screens** on them and
tests nothing.

### 8.2 Stage 1 — the exploratory screen (the four burned blocks)

Read on the existing snapshot, rows `[0, 45802)`, four outer blocks
`[26518,31339)`, `[31339,36160)`, `[36160,40981)`, `[40981,45802)`.

**Primary statistic:** per-fold outer net-return delta,
`ohlcv14_plus_derivatives_v1` − `ohlcv14`, on **XGBoost only**.

**Fold validity** (§8.4): a fold counts only if **each** of the two compared
arms realises at least **10** non-overlapping outer trades. Invalid folds are
reported and are excluded from **both** the numerator and the denominator.

**Improved means `delta > 0`, strictly. A delta of exactly zero is not an
improvement.** The claim under test is that the new information adds something,
and adding nothing is the null rather than a win. Zero is reachable in practice
— two arms that take no trades in a fold both return exactly 0.0 — which is why
it is settled here instead of when it happens.

**Stage 1 continues only if all three hold:**

1. at least **3** of the four folds are valid, counted over the blocks that are
   *available* under §8.0;
2. the combined arm improves on the control (`delta > 0`) in at least **3** of
   the valid folds;
3. the mean delta over valid folds is **> 0** *and* the worst valid fold's delta
   is **≥ −0.02**.

Condition 3 is what a bare fold count cannot say: P2b had two arms with a
positive mean while improving one or two folds, and the mirror failure — three
small wins and one catastrophic loss — passes a fold count and is not a result
anyone should spend a holdout on.

**What stage 1 is:** a screen with a false-positive rate near 0.31 under the
coin null. That is stated, not hidden, and it is acceptable *for a screen*
because the cost of a false continuation is exactly one holdout evaluation, and
the holdout is the thing that carries what evidential weight P4 has.

**What stage 1 is not:** evidence. A stage-1 pass is not a finding, is not
reported as one, and does not appear in `artifacts/README.md` as anything other
than an exploratory screen.

**If stage 1 fails, the holdout is not opened.** P4 is negative, the exploratory
numbers are frozen and published as negative, and there is no re-fit. This
sentence exists to close the "it was almost good, let's just look" door before
anyone is standing in front of it.

### 8.3 Stage 2 — the single-use holdout

Only if stage 1 continued. Everything is frozen before it runs: the eight
columns, their windows and clips, the model and its unchanged P2a configuration,
the inner-only threshold rule, the cost model, the universe rule.

- **One evaluation.** One arm pair (combined vs control), one model, one region.
- **Training** is rows `[0, 40981)`, **selection** is rows `[40981, 45802)`, and
  **evaluation** is P4-HOLD, `[45802, 48211)`. Those three ranges are values in
  `nn/p4_preregistration.py` (`STAGE_2_TRAIN_ROWS`, `STAGE_2_SELECTION_ROWS`,
  `STAGE_2_EVALUATION_ROWS`), inside the hashed payload: moving any of them
  moves the preregistration hash. They were prose here and nothing else, which
  meant the three numbers deciding what stage 2 fits, selects and reports on
  could be changed by an edit that moved no hash.
- The threshold is selected on the block **immediately preceding** the holdout,
  exactly as every fold in this programme selects on the block before its own.
  Nothing is selected on P4-HOLD.
- It is scored once and never re-scored, with the fold-boundary horizon purge
  already in the runner. Nothing is fitted or selected on a row inside P4-HOLD.
- Both arms are scored on the same rows, from the same file, in the same run.

**And the region is mechanically closed until all of that is true.**
`nn/p4_holdout.py` is the door: `assert_stage_one_rows` and
`assert_stage_one_bound` refuse any stage-1 row set or snapshot reaching row
45802 or beyond, so the screen cannot read the region it is screening in order
to decide whether to open; `assert_holdout_release` refuses unless the ledger
says the region is unspent, the stage-1 report was produced under *this*
preregistration hash, the availability gate passed, and the continuation rule
passes. See §9.3.

**What to expect, said in advance so that a thin result is not a surprise that
invites a second look.** P4-HOLD is 2,409 rows — half an outer block. Every
prior checkpoint's outer folds realised between 4 and 118 trades on 4,821 rows,
so a proportional expectation for P4-HOLD is roughly **2 to 60 trades per arm**.
A meaningful part of the probability mass therefore lands in the *inconclusive*
row of §9 before anything is run. That is a property of this evaluation region's
size, it is stated here rather than discovered afterwards, and it is not a
reason to widen the region, lower the floor, or look twice.

### 8.4 Outer trade validity

> **A fold or holdout region counts as an observation of a comparison only if
> *each* of the two compared arms realises at least 10 non-overlapping outer
> trades in it.**

**Where the number comes from.** Not from a power calculation, and not from
taste: `nn.p2b.MIN_TRADES = 10` already declares, and has declared since P2b,
that a trading statistic computed on fewer than ten realised trades is too thin
to *select* a decision threshold on. It is incoherent to refuse to select on
four trades and then report a fold built on four as one of four temporal
observations. The evaluation floor is the same number the repository already
uses to mean "enough trades for this figure to mean something", applied to the
block being **reported** rather than the block being **selected on**.

**A higher bar was considered and rejected — on evidence, and this is worth
showing.** P3's frozen `xgboost × ohlcv14` control realised:

| fold | control trades | combined trades | control net return |
| --- | --- | --- | --- |
| 0 | 80 | 118 | −0.1016 |
| 1 | 11 | 12 | +0.0325 |
| 2 | **4** | 28 | −0.0084 |
| 3 | 16 | 21 | +0.1056 |

Fold 2's four trades carried exactly the same weight in the 3-of-4 count as fold
0's eighty. Four trades is four draws.

Twenty — twice the selection floor, on the argument that an *evaluation* claim
should need more exposure than a *selection* — is a defensible principle and
would have invalidated **three of those four folds**. No arm behaving like the
control this programme has been comparing everything against could then reach
three valid folds, ever. **Preregistering a bar that nothing can clear is not
rigour; it is a way of guaranteeing a negative and calling it a decision rule.**

So the floor is ten. Under it, exactly one of the four folds above is invalid
(fold 2, on the control's side), leaving three — which is precisely stage 1's
requirement, with nothing to spare.

**And that is the finding to carry out of this section, not the number.** With
the existing threshold rule and horizon, this design's folds sit *at* the edge
of being computable statistics rather than comfortably above it. Exposure is
reported per fold beside the trade count (P3's control ranged from 0.5% to
10.1% of candles in a position) but is deliberately **not** a second gate: two
gates is two knobs. The thinness is recorded as a limitation of P4 and as a
reason a future generation should revisit the threshold rule — before its
results, not after them.

## 9. What each outcome means, and what happens next

Fixed before the run exists.

### 9.0 Before any of them: not evaluable is not negative

If the availability gate of §3.6 and §8.0 fails, **nothing was measured**. The
outcome is:

| label | reason code | classification | what happens |
| --- | --- | --- | --- |
| `not_evaluable` | `insufficient_coverage` | **not a research result** | Record the per-block coverage and stop. Do not run stage 1 on the blocks that did survive, do not open the holdout, and do not report P4 as negative evidence about derivatives positioning. |

This row exists because the alternative is the most tempting mistake available
here: a checkpoint that could not obtain its data, written up as a checkpoint
that looked and found nothing. "We could not get five years of open interest
from a public archive" is a fact about archives. It says nothing whatever about
whether funding, open interest and basis carry information, and a research
programme that let the two blur would have manufactured a negative out of a
404.

`nn/p4_preregistration.py::NOT_EVALUABLE_OUTCOME` and `EVIDENCE_CLASSIFICATION`
carry this in the hashed payload, so the classification cannot be softened after
the coverage is known.

### 9.1 The three outcomes of a holdout that was spent

| holdout outcome | condition | classification | what happens |
| --- | --- | --- | --- |
| **negative** | delta ≤ 0 | negative evidence | P4 is negative and closed. No re-fit, no window change, no second arm on these rows, and the holdout is not evaluated again. |
| **inconclusive** | delta > 0, but either arm has < 10 outer trades, **or** the combined arm's absolute net return after costs is ≤ 0 | hypothesis-generating | Recorded as hypothesis-generating. A follow-up needs a new research generation with its own evaluation data and may not re-use these rows. |
| **supported** | delta > 0, both arms ≥ 10 outer trades, combined absolute net return after costs > 0, and the sign of the delta survives 1.5× costs | **single-region supported — not confirmatory** | P4 is worth confirming. Confirmation is a **new research generation**: a new contract over a market or a time region this programme has not evaluated. |

**"Supported" is the ceiling.** One never-sealed region of about 2,400 rows and
tens of trades cannot carry the word *confirmatory*, and no amount of favourable
arithmetic on it will change that. The classification is a property of the
evaluation data, fixed here, not a property of the number that comes back.

There is no fourth row here, and §9.0 is not one: it is the outcome of never
reaching this table at all.

### 9.2 Styx

The sealed test block at `2025-08-27T23:00:00+00:00` is **not** opened, **not**
moved, and **not** available to resolve an ambiguous P4 result under any
outcome. It is not a tiebreaker, it is not a "if supported, confirm on Styx"
step, and P4-HOLD is not a substitute for it — P4-HOLD was never sealed, which
is exactly the difference.

### 9.3 P4-HOLD is spent once, by one checkpoint, ever — or retired unspent

Everything above is a promise. `nn/p4_holdout.py` is the mechanism, and
`data/research/p4_holdout_ledger.json` is the state it reads. All of it is
**outcome-blind**: it reads row indices, the ledger, and the counters a stage-1
report declares about the *burned* blocks. It never reads a price, a label, a
return or a prediction from inside the region, and no function in it returns
holdout data. Deciding whether the holdout may be opened must not require having
looked at it.

**Stage 1 cannot reach it.** `assert_stage_one_rows` refuses any row index at or
past 45802 and `assert_stage_one_bound` refuses any row *range* ending past it,
so a fold plan or a snapshot manifest cut one block longer is a named refusal
rather than a silent widening. Today's committed snapshot holds `[0, 45802)` and
therefore cannot reach the region — this turns that fact about a file into a
checked precondition, because a later export is exactly how it would stop being
true.

**It opens only on a frozen, matching stage-1 pass.** `assert_holdout_release`
requires four things, none of which is a judgement call: the ledger says
`unspent`; the stage-1 report was produced under *this* preregistration hash, so
a pass computed under an edited rule does not open it; the availability gate
passed; and §8.2's continuation rule passes on that report.

**One evaluation, one checkpoint, ever.** `record_spend` writes the ledger to
`spent` and every later release attempt is refused by name. A second reading of
these rows is not a fresh holdout.

**And if P4 never spends it, it is retired anyway.**

> If P4 ends without opening P4-HOLD — stage 1 failed, the availability gate
> failed, the checkpoint was abandoned — `record_retirement` marks the region
> `retired` and no later checkpoint may treat it as fresh.

This is the rule a future P4b or P5 would otherwise argue its way around, so it
is written down now, while nobody has a result to defend. By the time P4 ends,
its stage-1 numbers are published. A later design that reads them, retunes
against them, and then presents these same rows as an independent holdout is
using an adaptive region while calling it fresh — the rows informed a design
decision whether or not anyone scored them. Retirement does not forbid
*describing* the region; it forbids treating a result on it as independent
evidence.

**None of this upgrades anything.** Spending P4-HOLD does not make P4
confirmatory. Its maximum label is **single-region supported, never
confirmatory**, and the ledger says so in the file.

### 9.4 The stopping rule, in one sentence

**Every path above ends the checkpoint.** There is no branch on which P4 is
re-fitted, re-windowed, re-costed, re-armed or re-scored against the same rows,
and there is no branch on which a near miss becomes a reason to look again.

## 10. Model families

| role | model | configuration |
| --- | --- | --- |
| primary | `xgboost` | the unchanged predeclared P2a configuration |
| secondary | `logistic_regression` | unchanged |
| secondary | `lightgbm` | unchanged |

**One primary, chosen before results.** XGBoost is P2a's strongest OHLCV14
family and is the model every information-set checkpoint since has reported
against. Making it the *only* model the decision rule reads takes P4 from six
primary comparisons to one, which is the largest single reduction in
researcher degrees of freedom available here.

The two secondary models are run and reported in full — a family that behaves
differently is worth knowing about — but they cannot change the answer, and a
secondary model that improves while the primary does not is reported as exactly
that.

**No new architecture.** No neural model, no attention, no sequence model beyond
what the flattened window already gives the tabular estimators. The question is
about an information set; adding a model class would answer a different one and
would add a dimension nothing here is powered to resolve.

Every choice P4 introduces, and the sentence that closes it.

| whether a zero delta counts as improvement | §8.2: it does not. `delta > 0`, strictly. |
| what stage 2 fits, selects and reports on | three row ranges inside the hashed preregistration, §8.3. |
| what an availability failure means | §9.0: `not_evaluable` / `insufficient_coverage`, and not a negative result. |
| who may open the holdout, and how often | §9.3: once, one checkpoint, gated by `nn/p4_holdout.py`, retired if unspent. |
| how many features | exactly eight, named in §5. No additions, no substitutions. |
| trailing windows (9, 24, 30, 168) | declared per feature in §5; no window may be re-chosen at any point. |
| clips | declared per feature in §5. A clip is a domain bound, not a threshold to tune. |
| venue and instrument | Binance USD-M `BTCUSDT` perpetual, §3. |
| which model decides | one: `xgboost`, §10. |
| which comparison decides | one: combined vs control, §8.2. |
| horizon and target | unchanged from v4, §7.1. Changing them is a different question and a different checkpoint. |
| cost model | unchanged from v4, with a fixed 1.0×/1.5×/2.0× sensitivity reported for every arm, §7.2. |
| sample universe | one intersection rule, §6.2, applied identically to every arm, with the control re-run on it. |
| which folds count | a fold in which either compared arm realises fewer than 10 outer trades is invalid, §8.4. |
| whether to open the holdout | only on a stage-1 pass, once, from a file stage 1 cannot reach, §6.3. |
| what a result means | §9, fixed before the run. |

**Explicitly forbidden after any P4 result is seen:** feature-window shopping,
model shopping, horizon shopping, cost shopping, arm deletion, regime deletion,
fold re-splitting, re-running the holdout, and adding a "v2" of any feature
family to the same checkpoint.

**One accounting note.** Three arms × three models = nine cells will be run and
all nine will be reported. Only one comparison decides. Reporting all nine is
not multiplicity — hiding six of them would be.

## 12. Research classification

> **Adaptive on the four exploratory blocks; single-region and never-sealed on
> the holdout. P4 cannot produce confirmatory evidence.**

Recorded in every P4 artifact's own payload, as `adaptive_status` already is for
P2b, P2c and P3, so that a reader who never opens this document still gets the
label with the number.

Every label P4 can end with, as one table, in
`nn/p4_preregistration.py::EVIDENCE_CLASSIFICATION` and therefore inside the
hash:

| label | reached when | is it a research result? |
| --- | --- | --- |
| `not_evaluable` | the availability gate failed (§9.0) | **no** — nothing was measured |
| `screened_out` | the gate passed and stage 1 did not continue | exploratory, on burned blocks |
| `negative` | the holdout was spent and the delta was ≤ 0 | yes |
| `hypothesis_generating` | the holdout was spent and the result was inconclusive | yes |
| `single_region_supported` | the holdout was spent and the result was supported | yes — **and this is the ceiling** |

## 13. What must exist before P4 runs

A checklist, so that "preregistered" does not quietly come to mean "started".

- [ ] acquisition tool with `--plan` and `--probe`, no network in `--plan`
- [ ] the availability window established from metadata, and the §3.6/§8.0 gate applied
- [ ] the funding CSV layout matched against §3.0b's allow-list, or refused
- [ ] a snapshot exporter and a fail-closed verifier that recomputes every claim
- [ ] the verifier called from inside the only function that loads the source
- [ ] a value-level cross-source check with justified explicit tolerances
- [ ] the eight columns implemented against §5, with a spec hash
- [ ] the §4.4 leakage battery, each item with a positive control, **passing**
- [ ] `P4` registered in `nn.information_sets.CHECKPOINTS` with its three arms
- [ ] every stage-1 row set and snapshot passed through `nn.p4_holdout`
- [ ] the P4-HOLD snapshot exported, verified, and left uninspected
- [ ] this document unchanged, and its hash recorded in every cell

Nothing on that list is done. That is the correct state for a preregistration.

The ledger at `data/research/p4_holdout_ledger.json` says `unspent`, and no
Python file in this repository has read a row of `[45802, 48211)`.
